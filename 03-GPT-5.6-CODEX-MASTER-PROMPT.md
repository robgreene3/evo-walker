# GPT-5.6 Codex Master Prompt - Research and Build EvoWalker End to End

Paste this into Codex at the root of a new or existing repository. Add the accompanying `AGENTS.md` to the repository root first.

## Goal

Research, design, implement, verify, document, and prepare a release-quality MVP of **EvoWalker**: a modern browser-based spiritual successor to the breve Walker artificial-life demo.

The finished application must let a user start a seeded evolutionary locomotion experiment, observe physically simulated articulated creatures improve across generations, replay and inspect champions, understand fitness components and ancestry, and save/export/import experiments reproducibly within documented tolerance.

Do not stop at a report, plan, scaffold, mock, or partial vertical slice. Continue through safe in-scope reversible work until the complete MVP definition of done passes or a precise authority, safety, legal, product-decision, or evidence boundary requires user input.

## Mode

Infer from the repository:

- empty or scaffold-only: `CREATE`;
- functioning but incomplete EvoWalker project: `IMPROVE`;
- research-only request: `UNDERSTAND`;
- use `REBUILD` only with explicit authorization or strong evidence that repair is lower-value than replacement.

## User and critical outcome

- Primary users: curious non-specialists, students, educators, developers, and artificial-life enthusiasts.
- Job: run and understand embodied evolutionary experiments without installing a specialist research environment.
- Critical journey:
  1. open the app;
  2. start the default seeded experiment;
  3. watch generation progress while the UI stays responsive;
  4. replay and inspect the current champion;
  5. view lineage and component fitness;
  6. save/export the experiment;
  7. import/load it and recover equivalent state within documented tolerance.

## Target architecture for a new repository

Prefer a strict TypeScript workspace with:

- `packages/core`: explicit PRNG, genomes, controllers, genetic operators, fitness, validation, experiment schema and serialization;
- `packages/sim`: Rapier world, articulated phenotype construction, episode stepping, scoring, reset, snapshots;
- `packages/worker`: batch evaluation, worker pool, cancellation, progress protocol;
- `apps/web`: React controls, Three.js champion playback, charts/status, local persistence, import/export;
- `packages/benchmarks`: canonical configurations, seeds, reproducibility checks, statistical improvement gates.

Preferred technologies: TypeScript, Vite, React, Three.js, Rapier 3D WASM, Web Workers, Vitest, Playwright, and a runtime schema validator.

Use an existing sound architecture rather than replacing it merely to match this layout. Any material deviation must be supported by evidence and recorded.

## Scope and boundaries

### In scope

- one or a small set of fixed-topology articulated creatures;
- periodic joint controller genes such as amplitude, frequency, phase, and offset;
- seeded population-based genetic algorithm;
- tournament selection, elitism, crossover, bounded mutation;
- fixed-duration evaluation episodes;
- component fitness based on centre-of-mass progress with explicit penalties/bonuses;
- invalid-run handling;
- off-main-thread population evaluation;
- visible champion replay;
- generation progress, statistics, component fitness, genome and lineage inspection;
- start, pause, resume, restart, speed, and cancellation controls;
- versioned local save/load and JSON import/export;
- reproducibility and learning-improvement benchmarks;
- responsive and accessible desktop/mobile UI;
- tests, documentation, decision records, and release verification.

### Out of scope for the MVP

- evolved morphology;
- neural controllers;
- novelty search, MAP-Elites, or other quality-diversity systems;
- ecology, predation, mating, resources, or open-ended evolution;
- accounts, backend, cloud saves, multiplayer, payments, analytics, or external APIs;
- mobile-native, VR, or AR packages.

Do not silently expand scope. After MVP completion, morphology evolution may be proposed as a separately approved phase.

### Must preserve

- user changes and material existing behavior;
- data compatibility unless a documented migration is supplied;
- strict separation between simulation truth and rendering/UI;
- local-first privacy;
- accessible critical journey;
- versioned experiment provenance.

### Allowed without asking

- read-only inspection and public primary-source research;
- reversible repository-local edits;
- normal source/test/config/documentation additions in scope;
- running existing local install, format, lint, typecheck, test, benchmark, build, and browser automation commands.

### Requires approval

- backend, database, account system, cloud service, analytics, or paid API;
- destructive migration or deletion of user data/material work;
- deployment, publication, purchases, external communication, or production changes;
- consequential dependency with unclear licence, weak maintenance, native executable risk, or broad transitive impact;
- primary-stack replacement after the implementation baseline is accepted;
- any deferred feature.

## Hard invariants

- Never call `Math.random()` in experiment-affecting code.
- One explicit persisted PRNG drives every evolutionary random choice.
- Physics uses a fixed timestep and documented substep policy.
- Episode reset leaves no prior creature, world, controller, or metric state.
- Imported data is untrusted and validated before use.
- Simulation data contains no NaN or Infinity at persistence or UI boundaries.
- Rendering and React never own or mutate authoritative simulation state.
- Fitness is decomposed and inspectable; do not expose only an opaque score.
- Measure centre-of-mass progress, not the furthest body part.
- Do not claim bitwise or cross-platform determinism unless directly proven.
- Every factual claim in research or documentation has a verifiable source or is labelled inference/unknown.
- Do not claim a command ran or a behavior was inspected unless directly observed.

## Evolution baseline

Begin with the smallest credible, inspectable system:

- fixed body plan with approximately 4-8 actuated joints;
- per-joint periodic controller parameters;
- bounded parameters and outputs;
- tournament selection;
- small elite count;
- uniform or arithmetic crossover;
- per-gene bounded Gaussian mutation;
- persisted seed;
- configurable population and generation cap;
- plateau/user-stop termination;
- diversity telemetry such as duplicate rate or genotype distance.

Fitness must report components. A suitable baseline is:

`fitness = forwardProgress + uprightBonus - fallPenalty - energyPenalty - lateralDriftPenalty - invalidPenalty`

Add a settling interval and other guards needed to prevent ballistic or contact exploits. Tune only from benchmark evidence, not visual preference alone.

## Required vertical-slice sequence

### Slice 1 - Baseline and repository health

- Create or verify the workspace.
- Establish exact install, run, format, lint, typecheck, test, benchmark, end-to-end, and production-build commands.
- Add a short implementation plan and evidence ledger.
- Get the empty/minimal app through the full basic toolchain.

Acceptance: clean install and basic checks are reproducible from documented commands.

### Slice 2 - One deterministic creature episode

- Construct the world and one articulated creature.
- Drive joints from explicit controller parameters.
- Run one fixed-duration episode.
- Compute component fitness.
- Reset and replay.
- Add tests for bounds, termination, invalid values, and state leakage.

Acceptance: identical supported-environment seed/config repetitions produce equivalent episode metrics within a predeclared tolerance and no reset leakage.

### Slice 3 - Evolution engine

- Implement population creation, evaluation, ranking, selection, crossover, mutation, elitism, lineage, and generation transition.
- Keep it independent of React and Three.js.
- Add operator and invariant tests.
- Create canonical benchmark seeds.

Acceptance: across the canonical seed set, best and/or median fitness meets a predeclared improvement gate over generation zero without relying on one lucky run.

### Slice 4 - Worker evaluation

- Move batch evaluation off the main thread.
- Define a typed protocol.
- Add progress, cancellation, error propagation, and cleanup.
- Compare direct and worker evaluation within tolerance.

Acceptance: training does not freeze ordinary UI interaction; cancellation leaves a clean recoverable state.

### Slice 5 - Critical UI journey

- Create the Three.js champion scene and camera controls.
- Build React controls for start, pause, resume, restart, speed, and cancellation.
- Show generation, progress, best/median fitness, component fitness, status, genome, and lineage.
- Do not render every evaluated creature.
- Support initial, running, paused, completed, cancelled, loading, error, and no-champion states.

Acceptance: the complete critical journey works by keyboard and pointer on representative desktop and mobile layouts with no runtime/console errors.

### Slice 6 - Persistence and recovery

- Define a versioned experiment schema.
- Persist configuration, seed, PRNG identity/version, physics parameters, generation state, genomes, lineage, fitness components, and build/schema version.
- Implement local save/load plus JSON import/export.
- Reject corrupt, oversized, invalid, and unsupported-version data safely.
- Document migration policy.

Acceptance: export/import restores a benchmark experiment and champion replay within documented tolerance; failure states provide useful recovery guidance.

### Slice 7 - Release gate

- Run all checks from a clean state.
- Inspect representative desktop and mobile screenshots and actual interactions.
- Exercise reduced motion, keyboard use, focus, names, semantics, reading order, contrast, and status messages.
- Profile worker throughput and UI responsiveness with controlled repeated runs.
- Complete documentation.

Acceptance: every definition-of-done item is backed by observed evidence.

## Evaluation plan

Before tuning, define:

- supported development/runtime environment;
- canonical creature and environment configuration;
- canonical seed set;
- generation count and population size;
- primary measure;
- statistical improvement gate;
- reproducibility tolerance;
- performance benchmark and measurement protocol;
- hard guardrails: no invalid propagation, no UI lockup, no worker leakage, no data corruption;
- falsifiers and stop rules.

Suggested primary measure: distribution of best-of-generation forward progress or aggregate fitness at generation 30 compared with generation 0 across multiple seeds.

Do not make the benchmark a brittle exact-score snapshot. Use justified tolerances or statistical envelopes and report variance.

## UI and accessibility requirements

Use a clear, restrained interface that prioritizes the creature and experiment state.

- Define a minimal token set if no design system exists.
- Provide a useful default experiment.
- Use semantic controls and headings.
- Every control has an accessible name and visible focus.
- Status changes are conveyed without relying only on animation or colour.
- Honour reduced motion.
- Ensure keyboard order matches visual/logical order.
- Prevent dense charts or 3D motion from blocking the main controls.
- On small screens, preserve start/stop, status, champion view, and essential metrics before secondary inspection panels.
- Avoid manipulative pet-death or guilt mechanics; this is an experiment sandbox.

## Definition of done

The MVP is done only when all of the following are observed:

1. A new user can start the default seeded experiment without reading documentation.
2. A population completes at least 30 generations without UI lockup, unrecoverable worker error, simulation corruption, or NaN/Infinity propagation.
3. The canonical benchmark suite meets its predeclared evolutionary improvement gate.
4. The current champion can be replayed and its genome, lineage, aggregate fitness, and fitness components inspected.
5. Pause, resume, restart, speed, and cancellation controls recover cleanly.
6. Save/export then import/load restores equivalent experiment state within the documented tolerance.
7. Invalid and incompatible imports fail safely with a clear message and recovery path.
8. The critical journey works on representative desktop and mobile viewports.
9. Semantic structure, keyboard navigation, visible focus, accessible names, contrast, reading order, status communication, and reduced-motion behavior pass inspection.
10. Exact format, lint, type, unit, integration, benchmark, end-to-end, and production-build checks pass.
11. Documentation covers setup, architecture, algorithms, fitness, experiment format, reproducibility limits, supported environment, known risks, and rollback/recovery.
12. No deferred feature was silently introduced.
